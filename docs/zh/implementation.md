# Proactive AI 的实现原理

[English](../en/implementation.md) | [中文](implementation.md)

Proactive AI 使用现成的大语言模型提出对话计划，再由程序管理时间、保存队列、检查计划并执行发送。没有为此训练一个新模型，也不要求模型在两次调用之间持续运行。JSON 是模型表达计划的接口；主动交互来自模型与事件驱动程序的协作。

本文从一次对话解释实现过程。需要精确字段约束时，参阅[时间对话协议](protocol.md)；需要配置模型时，参阅[模型提供商指南](model-providers.md)。

## 从消息到下一次判断

一次模型调用不再只回答“现在说什么”，而是提出“现在如何回应、以后还要做什么、之前的安排是否需要改变”。完整循环是：

```text
用户发来消息 / 队列行动到期 / 对话起搏
                 ↓
程序整理最新上下文和待执行计划
                 ↓
大模型生成 JSON 候选计划
                 ↓
程序验证并一次性更新状态
                 ↓
显示可见消息，保存未来行动，等待下一个事件
```

每条用户消息都会独立记录，但不必对应一次模型调用。Demo 的输入协调器默认使用 350 毫秒的合并窗口，让短时间内连续发送的消息进入同一次判断。如果模型推理期间又收到消息，协调器会丢弃旧快照产生的候选计划，再基于全部未处理输入重新规划；旧计划不会先显示出来再撤回。

## 模型每次看见什么

模型适配器把以下信息组成当前调用的上下文：

- 当前时间、状态修订号，以及触发本次判断的事件。
- 尚未处理的用户消息和近期对话。没有新输入时，新消息列表可以为空。
- 待执行队列，以及其中已经到期、需要明确处理的行动。
- 下一次起搏、主动联系许可、联系截止时间，以及本次是否必须产生可见消息。

系统提示说明各字段的含义和行为规则，例如允许沉默、不要逐条机械回应用户、新信息可以使旧计划失效、每项到期行动必须得到明确处置。每次请求都会重新携带上下文，不依赖模型服务在调用之间自行记住队列。

当前实现通过 OpenAI-compatible Chat Completions 调用模型。支持严格结构化输出的提供商使用 `response_format.type = "json_schema"`，并设置 `strict: true`。其他兼容接口可以使用 `json_object` 或仅靠提示生成 JSON；后两种模式会在提示中提供完整的计划 Schema。普通 JSON 模式只约束 JSON 格式，严格结构化输出进一步约束字段和类型，但二者都不能保证模型的情境判断正确，仍需本地验证。参见 [OpenAI Docs 对两种模式的说明](https://developers.openai.com/api/docs/guides/structured-outputs#structured-outputs-vs-json-mode)。

当前适配器没有使用 function calling，也不依赖 LiteLLM SDK；LiteLLM 可以作为可选的兼容网关，模型与执行引擎之间仍使用同一种计划接口。

## JSON 表达的是计划而不只是回复

假设用户连续说“我明天有个重要面试”和“我有点紧张”。下面是一份完整的说明性候选计划，符合当前输出结构；它不是对真实模型必然输出内容的约定：

```json
{
  "schema_version": "1",
  "immediate_messages": [
    {
      "content": "重要面试前紧张很正常。",
      "reason": "回应用户表达的紧张情绪。"
    },
    {
      "content": "我们可以先从一个具体的小步骤开始准备。",
      "reason": "把准备过程变得更容易开始。"
    }
  ],
  "scheduled_actions": [
    {
      "type": "send_message",
      "delay_seconds": 600,
      "content": "可以选一个最能体现你能力的经历，试着用两分钟讲清楚。",
      "reason": "稍后提供一条准备建议，发送前再次确认是否适用。"
    },
    {
      "type": "reconsider",
      "delay_seconds": 7200,
      "content": null,
      "reason": "两小时后根据最新情境判断是否需要继续跟进。"
    }
  ],
  "queue_mutations": [],
  "accepted_due_action_ids": [],
  "next_pacemaker_seconds": 1800,
  "internal_summary": "现在简短回应，保留一项准备建议和一次稍后的跟进判断。"
}
```

各字段承担不同职责：

| 字段 | 作用 |
| --- | --- |
| `schema_version` | 标识计划协议版本。 |
| `immediate_messages` | 本次希望立即呈现的消息列表，可以为空或包含多条。 |
| `scheduled_actions` | 新增未来行动，每项有自己的类型、延迟和理由。 |
| `queue_mutations` | 对已有行动提出取消、推迟或替换；通过稳定 ID 指定目标。 |
| `accepted_due_action_ids` | 明确确认本次允许执行的到期行动，不是无条件发送指令。 |
| `next_pacemaker_seconds` | 建议下一次起搏间隔；`null` 表示不提出新的间隔。 |
| `internal_summary` | 简短记录决定及依据，不是模型的隐藏推理，也不是聊天消息。 |

`send_message` 保存已经准备好的文字。`reconsider` 的 `content` 必须为 `null`，因为它保存的是未来再决定的机会，不是提前写好的一条回复。模型只提出相对延迟；程序分配行动 ID，并依据当前事件时间计算最早执行时点。

两条 `immediate_messages` 属于同一次状态更新，并没有人为打字间隔。若希望两条消息之间相隔几秒，后面一条应成为带正延迟的 `send_message`，并在到期时复核。

## 程序怎样执行和修改计划

收到 JSON 后，程序不会立刻逐条执行，而是先完成两层检查：

1. **结构检查**：用 Zod 验证字段、类型、长度和取值，以及两类行动的内容约束。
2. **状态检查**：验证目标 ID 是否仍待执行、被接受的行动是否已经到期、同一行动是否被冲突处理、是否遗漏到期行动，以及主动联系策略是否允许可见输出。

通过检查后，引擎在状态副本上应用计划，再整体返回更新后的状态。这里的“原子” 是指候选计划整体生效或整体不生效，不是已经实现了跨数据库或外部消息服务的分布式事务。获准发送的到期消息按到期时间和稳定 ID 排序，再按列表顺序加入新生成的即时消息。

以上面的初始计划为例，可以出现两条不同的后续路径：

| 情形 | 发生的处理 |
| --- | --- |
| 没有新变化，10 分钟后建议到期 | 程序再次调用模型；模型确认该行动仍合适后，程序才发送保存的建议。 |
| 5 分钟后用户说“面试取消了” | 新消息与待执行队列一起交给模型；模型可取消准备建议和两小时后的跟进，程序验证后将它们标记为 `cancelled`。 |
| `reconsider` 到期且未被取消 | 再次取得当前上下文；模型可产生新回复、安排后续行动或保持沉默，并明确处理这次到期机会。 |

取消是更新行动状态，不是抹掉历史记录。发送时复核确保到期行动经过一次最新判断，但无法替模型保证语义判断一定正确：如果模型错误地确认了不合适的内容，格式和队列检查本身不一定能识别这一点。

模型超时、拒绝回答、输出截断或计划无效时，不发送候选消息，也不应用候选队列修改。引擎保留未处理输入与待执行行动，另按恢复规则安排重试；恢复规则可以调整重试时点，这与执行失败计划的部分内容不同。

## 没有用户输入时为什么还能发话

模型本身不会设置一个后台闹钟。一次 API 调用结束后，后续等待由程序负责。对话起搏器保存下一次唤醒时点；到期后程序即使没有收到新用户消息，也会组织上下文并再次调用模型。队列到期同样可以触发判断。

起搏不意味着必须发言。如果计划既没有即时消息，也没有被接受的到期发送，这次判断就不会产生可见消息。若模型想推迟首次回复，可以现在不发言，安排一项未来的 `reconsider`，届时再判断。

可选的有界沉默策略进一步保存联系截止时间。截止时间之前允许保持沉默；到达截止时间且外部规则允许联系时，运行时要求下一份有效计划产生可见消息。如果模型仍只提出沉默，计划会被拒绝，但截止义务不会被清除。程序也不会自行补造一条固定问候来冒充模型输出。

暂停主动联系会阻止没有待处理用户输入时的可见输出，但仍允许回应用户发来的消息；暂停不会清除截止时间，明确关闭有界沉默策略才会清除它。能否最终联系仍以程序持续运行、联系获得许可且模型规划成功为前提。

Web Demo 中，核心状态与调度在浏览器运行，服务端路由负责模型调用；命令行测试则直接调用同一个适配器和引擎。这两条路径都不会让模型绕过执行层直接发送。在当前 Demo 中，“发送”具体是把消息加入对话状态并呈现在界面，而不是发送微信消息、邮件或系统推送。

## 如何运行和验证

在仓库根目录安装并启动：

```bash
pnpm install
pnpm dev
```

首先可以使用无需密钥的“场景演示”：播放控件驱动预设事件与提案经过实际引擎执行，不提供自由输入框。连接真实模型时，按照 [模型提供商指南](model-providers.md)配置 `apps/demo/.env.local`，然后切换到“真实对话”。密钥只写入本地配置，不写入前端源码或 Git。

引擎中的时钟与规划器仍相互独立。界面将场景演示与真实对话分开，状态不会混合。真实对话默认使用真实时间，首条消息后开始自动判断，高级控制中可切换模拟时间。真实时间跟随电脑时钟，页面恢复后会把错过的唤醒合并为一次基于最新情境的判断。切换到场景演示会停止模型的自动调度，具体见 [Demo 指南](demo.md)。

运行不调用付费模型的检查：

```bash
pnpm test
pnpm typecheck
pnpm lint
```

需要真实 API 集成检查时，另行手动运行 `pnpm model:validate`。该命令会产生费用，包含初始规划、到期确认、取消、起搏、暂停与恢复联系六个决策场景；用户输入与事件时间由测试控制，计划来自真实模型。请求上限、报告与恢复方式见 [有调用上限的真实模型验证](model-providers.md#有调用上限的真实模型验证)。普通 Demo 不共享该测试命令的请求上限，开启真实模型和真实时间后要留意持续调用成本。

## 当前实现的边界

- 当前模型上下文使用最近 40 条对话，并另行包含全部待处理用户消息与待执行队列；还没有接入长期记忆检索。对话和计划的连续性首先由应用状态维持。
- Live Demo 在页面关闭时不会继续运行。持续后台服务需要把状态、调度和发送迁移到可靠的服务端设施，并补充身份验证、限流和跨设备一致性。
- 当前联系开关提供外部许可结果，但并未完整实现免打扰日历等策略。
- 严格 JSON 输出、规则检查和一次真实模型测试分别验证不同层次，不能据此推断任何模型、任何情境下都能给出恰当的回复。详细检查见[协议一致性轨迹](protocol-conformance.md)。
