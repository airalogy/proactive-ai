# 时间对话协议

[English](../en/protocol.md) | [中文](protocol.md)

本文规定 `@proactive-ai/core` 当前实现的可执行协议。它把大模型的判断，与确定性的时间、队列和消息发送语义分开。

## 状态与事件

在时间 `t`，对话状态表示为：

```text
S(t) = <H(t), Q(t), C(t), P(t), L(t)>
```

- `H(t)`：带时间戳的用户与 AI 消息历史；
- `Q(t)`：持久化的未来行动队列；
- `C(t)`：逻辑时钟、修订号和序列计数器；
- `P(t)`：对话起搏器的间隔与下一次唤醒时间；
- `L(t)`：有界沉默配置、最近一次可见 AI 消息、下一次联系截止时间，以及当前外部策略是否允许主动联系。

引擎识别三种触发事件：

```text
E = user_message | pacemaker | queue_due
```

消息到达与规划器执行是两个不同阶段。用户每次发送都会先被记录为一条独立、带时间戳的消息，并请求系统重新判断。协调器取得决策快照时，一次 `user_message` 触发可以引用一条或多条尚未由已提交计划处理的有序消息。读取并不等于处理完成；有效的沉默计划则完成处理。任何触发都会纳入全部未处理输入，包括失败后保留的消息，因此一次对话起搏可以包含零条或多条这类消息。一次 `queue_due` 事件还包含所有已到达 `not_before` 时间的待执行行动。

## 规划器输出

每次触发后，规划器都把当前状态与事件映射成一个时间计划：

```text
π(S(t), e(t)) -> <U, N, Δ, A, p, r>
```

- `U`：立即发送的零至八条消息；
- `N`：新增的零至十六个未来行动；
- `Δ`：对已有待执行行动的修改；
- `A`：经过重新检查后明确接受的到期行动 ID；
- `p`：可选的下一次起搏延迟；
- `r`：简短、可审计的决策摘要。

可移植的 JSON 形式如下：

```json
{
  "schema_version": "1",
  "immediate_messages": [
    {
      "content": "听起来这场面试对你很重要。",
      "reason": "acknowledge_emotional_context"
    },
    {
      "content": "你最担心的是哪一部分？",
      "reason": "invite_low_effort_next_step"
    }
  ],
  "scheduled_actions": [
    {
      "type": "send_message",
      "delay_seconds": 20,
      "content": "我又想到一个很实用的办法……",
      "reason": "short_burst_continuation"
    },
    {
      "type": "reconsider",
      "delay_seconds": 7200,
      "content": null,
      "reason": "follow_up_interview"
    }
  ],
  "queue_mutations": [],
  "accepted_due_action_ids": [],
  "next_pacemaker_seconds": 1800,
  "internal_summary": "现在先回应，稍后延续表达，并在更长时间后重新判断是否跟进。"
}
```

模型只输出相对时间 `delay_seconds`；确定性调度器再把它换算成绝对 `not_before` 时间。这样模型不会成为系统时钟或日期运算的事实来源。

## 队列行动

两种未来行动具有不同语义。

### `send_message`

保存适合短时间连续表达的预生成内容。到达 `not_before` 并不会自动发送。规划器必须先看到最新上下文，再把行动 ID 放入 `accepted_due_action_ids`；否则必须取消、改期或替换该行动。

### `reconsider`

只保留未来重新思考的机会，不提前确定措辞。到期后，它在重新规划完成时被消费；规划器届时可以继续沉默、发送新的即时消息，或再创建一个未来行动。

队列行动的状态变化为：

```text
pending -> delivered   （接受到期的 send_message）
pending -> consumed    （接受到期的 reconsider）
pending -> cancelled   （取消）
pending -> pending     （改期或替换）
```

## 队列修改

系统可以原子化地修改已有待执行行动：

- `cancel`：使行动失效；
- `reschedule`：设置新的相对延迟与原因；
- `replace`：替换预生成消息，也可同时修改延迟。

每项修改都指向稳定的 `target_id`。同一个计划不能修改同一行动两次，不能同时接受并修改同一行动，也不能修改非等待状态的行动。

## 原子发送不变量

最重要的安全不变量是：

> 每个到期行动都必须被观察它的同一份计划恰好处理一次；任何到期消息都不能在未经明确接受的情况下发送。

引擎会先验证整份规划结果，再执行任何用户可见行动。如果 JSON 解析、Schema 验证、模型传输或队列一致性检查失败，系统将以关闭方式失败：丢弃本次即时输出，不发送到期消息，把到期时间向后推一个短重试间隔，并安排起搏器重试。部分计划不会造成过时消息泄漏。

用户消息的处理标记只随有效计划一起提交。失败的输入会保留到后续用户事件、队列事件或对话起搏中再次处理。输入协调器在失败后返回恢复状态，而不立即循环重试；调用方通过所选时钟驱动已安排的重试。恢复过程可以更新重试时间，但不会应用候选消息或候选队列修改。

## 事件顺序与快照新鲜度

当队列行动与对话起搏具有相同时间戳时，先处理队列到期。获准执行的到期行动按 `not_before` 排序，同一时间的行动按稳定 ID 排序；规划器返回 ID 的先后不会改变发送顺序。被接受的预备消息先发送，随后按列表顺序发送新生成的即时消息。推进虚拟时间时，引擎会不断处理最早事件，直到到达目标时间。

每份候选计划都绑定生成其上下文时的状态修订号。如果规划器运行期间又有用户消息到达，当前修订号便会推进；协调器会在任何消息或队列修改提交之前丢弃旧候选计划，并立即把全部尚未处理的输入纳入下一次规划。因此，快速输入的合并属于执行层的决策快照语义，并不意味着用户的多次发送是同一个到达事件。

## 沉默

沉默由空的 `immediate_messages` 且没有接受到期发送来表示。它是一份正常成功的计划，而不是错误或模型漏答。因此，对话起搏器保证的是“再次判断”，不是“再次通知用户”。

启用有界沉默后，`deadline_at` 为这种原本合法的沉默设置上界。截止时间之前，规划器仍可继续沉默；到达截止时间且 `contact_allowed` 为真时，下一份合法计划必须产生至少一条可见消息。运行时会在提交任何计划内容之前检查这一条件。只包含沉默的计划将以关闭方式失败，截止时间保持不变，并安排后续重试。

每次可见 AI 消息都会更新 `last_visible_assistant_at`，并按 `max_silence_seconds` 推进下一截止时间。把 `contact_allowed` 临时设为假只会暂停执行，不会清除截止时间；只有明确关闭有界沉默策略才会清除它。对话起搏器的下一次唤醒时间也会被限制在允许联系的截止时间之前或与其相同。外部开关关闭期间，自主触发不能产生可见消息，到期的预生成消息必须推迟或取消；用户主动发来新消息后，系统仍可直接回应。

## 第一版边界

版本 1 有意保持范围收敛。它接收确定性的外部策略判断，但不在协议内部计算通知权限、免打扰时段、频率限制或领域安全规则；它也尚未定义多人频道、工具执行、记忆检索或分布式恰好一次发送。这些能力可以在时间对话协议的上层或下层补充，而不改变核心抽象。
